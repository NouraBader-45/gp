# Sprint 5 – Alert Management and Interactive Security Dashboard

## 1. Sprint Overview

Sprint 5 focuses on presenting the outputs of the previous security-analysis components to the user through alert-management functionality, mobile notifications, and an interactive mobile security dashboard.

The sprint consists of two main features:

1. Alert Management and Notification
2. Interactive Security Dashboard

This sprint does not perform threat detection or machine-learning analysis itself.

Instead, it consumes security events, device information, traffic statistics, risk information, and other outputs produced by previous system components and makes them accessible to the user through the Flutter mobile application.

---

## 2. Sprint Features

### 2.1 Alert Management and Notification

The Alert Management and Notification feature manages security alerts generated by previous system components.

The feature will support functions such as:

- Receiving generated security events
- Storing alerts
- Displaying alert severity or priority
- Tracking alert status
- Alert acknowledgment
- Mobile notification delivery

The exact interpretation of alert escalation will be finalized with the project supervisor before implementation to ensure that it remains within the prototype scope.

### 2.2 Interactive Security Dashboard

The Interactive Security Dashboard provides a user-friendly Flutter mobile interface for viewing security and network information.

The dashboard will present relevant information such as:

- Network status
- Connected devices
- Active alerts
- Traffic statistics
- Risk information
- Alert and incident history
- Network risk trends where available

The dashboard will obtain its data from the local backend rather than directly accessing detection-engine output.

---

## 3. System Flow

The general data flow is:

```text
Previous Security Components
        ↓
Security / Monitoring Data
        ↓
Backend
        ↓
SQLite
        ↓
FastAPI
        ↓
JSON
        ↓
Flutter Mobile Application
```

Alert notifications follow the general flow:

```text
Security Event
        ↓
Alert Management Logic
        ↓
Notification Decision
        ↓
Firebase Cloud Messaging
        ↓
Mobile Application
        ↓
User
```

Sprint 5 therefore acts as the user-facing integration layer between previously generated security information and the mobile application.

## 4. Implementation Approach

### 4.1 Alert Data Structure

Before implementing the alert interface, the system will define a consistent internal alert structure.

The required fields may include:

- Alert ID
- Device ID
- Timestamp
- Alert source
- Alert type
- Severity or priority
- Description
- Risk score, when available
- Alert status

The final schema will be coordinated with the outputs produced by previous system components.

### 4.2 Alert Storage

Security alerts will be stored locally using SQLite.

The implementation will include:

1. Defining the required alert table structure.
2. Storing newly received security events.
3. Retrieving active and historical alerts.
4. Updating alert status.
5. Supporting the information required by the mobile application.

A preliminary database schema is included in `schema.sql`.

A preliminary alert-management implementation is included in `alert_manager.py` to demonstrate storing, retrieving, and acknowledging local security alerts.

### 4.3 Alert Status Management

The prototype may use an alert lifecycle such as:

```text
New
 ↓
Viewed
 ↓
Acknowledged
```

The exact set of alert states will be finalized before implementation.

The prototype will avoid claiming that an alert is "resolved" unless the system has a defined mechanism for verifying resolution.

### 4.4 Alert Prioritization

The Alert Management component will consume severity or risk information produced by the appropriate security-analysis components.

Sprint 5 will focus on presenting and managing this information rather than rebuilding the risk-scoring mechanism.

High-priority alerts may be presented more prominently to the user.

### 4.5 Mobile Notifications

Firebase Cloud Messaging will be used for mobile push-notification delivery.

The implementation will include:

1. Integrating Firebase Cloud Messaging with the Flutter application.
2. Triggering notifications for selected security alerts.
3. Including relevant alert information in the notification.
4. Testing notification delivery.
5. Handling notification interaction inside the application.

Firebase Cloud Messaging will provide notification delivery only.

The project will implement the alert-management logic that determines which security events should generate notifications.

FCM integration is not implemented in the preliminary proof-of-concept files because it requires Firebase project configuration and mobile-application integration.

### 4.6 FastAPI Backend

FastAPI will provide RESTful endpoints between the local system data and the Flutter application.

Initial candidate endpoints may include:

- GET /devices
- GET /alerts
- GET /alerts/{id}
- PATCH /alerts/{id}/acknowledge
- GET /traffic/stats
- GET /risk
- GET /incidents

The exact endpoint names and response structures will be finalized during backend implementation.

A preliminary FastAPI implementation is included in `api_example.py` to demonstrate how alert information can be retrieved and updated through RESTful endpoints.

### 4.7 Flutter Dashboard

The Flutter mobile application will retrieve structured JSON data from FastAPI and display it through the security dashboard.

Candidate dashboard sections include:

- Network Overview
- Connected Devices
- Active Alerts
- Traffic Statistics
- Risk Information
- Alert History
- Incident History

The user interface will focus on presenting technical security information clearly for non-technical users.

Flutter interface implementation will begin after the backend data structures and API responses are finalized.

## 5. Build vs. Existing Technology Decision

### Alert Management

The alert-management logic will be implemented as part of the project.

The project will define:

- Alert data structure
- Alert states
- Alert retrieval
- Alert acknowledgment
- Notification conditions
- Alert presentation

### Mobile Notifications

Firebase Cloud Messaging is an existing external service and will be integrated rather than developing a notification-delivery infrastructure from scratch.

### Backend

FastAPI is an existing backend framework.

The team will develop the project's RESTful endpoints and backend logic using FastAPI.

### Database

SQLite is an existing local database engine.

The team will design the project's required tables, queries, and storage logic.

### Dashboard

The dashboard will be developed by the project team using Flutter and Dart.

Flutter provides the application framework, while the interface design and project-specific functionality will be implemented by the team.

## 6. Dataset, Model, and API Decisions

| Feature | Training Dataset | ML Model | Model Training | API / Service | Main Implementation |
|---|---|---|---|---|---|
| Alert Management | Not required | None | Not required | FastAPI | Custom project logic |
| Mobile Notifications | Not required | None | Not required | Firebase Cloud Messaging | Integration |
| Interactive Dashboard | Not required | None | Not required | Local FastAPI endpoints | Flutter application |
| Local Storage | Not required | None | Not required | None | SQLite integration |

### Dataset Decision

Sprint 5 does not require a training dataset.

The sprint consumes live and stored system data generated by other components.

### Model Decision

Sprint 5 does not train or execute its own machine-learning model for alert management or dashboard presentation.

Machine-learning detection and risk-analysis results are treated as inputs produced by other project components.

### API Decision

FastAPI will be used to develop the project's local RESTful API.

Firebase Cloud Messaging will be used as an external notification-delivery service.

The core dashboard and local alert data should remain accessible through the local system architecture.

## 15. Manageability

Sprint 5 is considered technically manageable because it does not require developing a new machine-learning model, detection engine, database engine, backend framework, or notification-delivery platform from scratch.

The sprint integrates established technologies:

- Flutter for the mobile application
- FastAPI for RESTful communication
- SQLite for local storage
- Firebase Cloud Messaging for mobile notification delivery

The project-specific implementation focuses on alert-management logic, API development, database integration, mobile interfaces, and integration between components.

To keep the sprint manageable, the dashboard will focus on the security information required by the project rather than implementing the functionality of a full enterprise security-management platform.

The included preliminary implementation files provide an initial proof of concept for local alert storage, alert management, and RESTful access to alert data.

## 17. Risks and Limitations

The main risks and limitations include:

- Sprint 5 depends on data structures produced by earlier sprints.
- Changes to earlier outputs may require changes to the backend API or Flutter models.
- Firebase Cloud Messaging requires external connectivity for push-notification delivery.
- Mobile notification behavior may vary depending on operating-system restrictions.
- The prototype is intended for home and small-business users rather than enterprise SOC operations.
- Alert acknowledgment indicates that the user has reviewed the alert; it does not automatically mean that the underlying security issue has been resolved.
- The dashboard presents available system information but does not directly block malicious network activity.
- The preliminary backend implementation covers alert-management feasibility only and does not represent the final mobile dashboard.
